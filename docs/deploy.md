# פריסה — הפרוטוקול המלא

## 8. פרוטוקול פריסה — קריטי, לקרוא פעמיים

**⛔ לא לפרוס בלי אישור (בקשת המשתמש 07/10/2026)**: פתיחת PR לפריסה — רק אחרי אישור מפורש של המשתמש באותה בקשה. קוד שנכתב בסשן אחר ולא נדחף — לא פורסים מיוזמתנו.

**שני מספרים — גרסת מערכת ומספר בנייה (12/10/2026, בקשת המשתמש; מ־1.0.0 = בנייה 395)** — כמו versionName + versionCode באנדרואיד:
- **`APP_RELEASE` = גרסת המערכת, SemVer `MAJOR.MINOR.PATCH`** — מה שהמשתמש רואה ("1.0.0 (395)" בהגדרות ← מתקדמות), התגית ב־git (`v1.0.0`), והכותרת ב־`CHANGELOG.md`. **עולה רק כשמשחררים לפרודקשן**: PATCH = תיקונים בלבד; MINOR = יכולת חדשה; MAJOR = שינוי שמשנה את דרך העבודה (מעבר דומיין, מבנה נתונים שלא תואם לאחור). אחרי 1.9.0 בא 1.10.0 (לא 2.0.0).
- **`APP_VERSION` ‏`vNNN` = מספר הבנייה** — עולה בכל PR שמשנה קבצי תוכן (מפתח המטמון, swgen, השומר, המנעול בין סשנים). לא מספר שמשתמש צריך לזכור.
- **⭐ ברירת המחדל = שחרור לייצור (26/10/2026, החלטת המשתמש — "בשלבי הפיתוח אין טעם להעביר כל שינוי דרך הניסוי")**: כל PR עם שינוי שהמשתמש מרגיש **מעלה את `APP_RELEASE`** (PATCH לתיקון/ליטוש, MINOR ליכולת) ומשתחרר לייצור. רק לניסוי — רק כשהמשתמש ביקש במפורש. גובר על הסעיף הבא.
- **הקצב**: כל מיזוג → סביבת הניסוי בלבד. לפרודקשן — רק PR ש**מעלה את `APP_RELEASE`** (`deploy.yml` מבקש אישור רק כשאין עוד תגית לגרסה). שינויים מצטברים בניסוי, ו־Claude **מציע** למשתמש לשחרר ("לשחרר את 1.3.0? בפנים: …") כשיש משהו שלם ובדוק. **תיקון דחוף** = אותו PR מעלה PATCH ומשתחרר מיד.
- **`CHANGELOG.md`** (עברית פשוטה, למשתמש — לא טכני; הטכני ביומן): כל PR עם שינוי שהמשתמש מרגיש מוסיף שורה תחת "## לא פורסם"; PR של שחרור מעביר אותן לכותרת "## X.Y.Z — תאריך". השומר דורש את הכותרת כשהגרסה עולה (`tests/deploy-guard.test.js`).
- **כותרות PR**: שחרור — "1.3.0 (412): …"; בלי שחרור — "(412): …".
- **רכיבים**: גרסה אחת לכל המערכת (מונוריפו) — התגית מסמנת את הקומיט של האתר, השרתון והעובד. ה־APK ממוספר בנפרד (`1.0.<ריצה>` ב־`android.yml`) — הוא רק מעטפת שמשתנה לעיתים רחוקות.

**פס פריסה אחד — PR אחד לכל גרסה (מ־v394, 12/10/2026; מחליף את "שני PR")**:
1. `APP_VERSION` ב־`app.js` = **המקום היחיד של הגרסה** (באזור `<core>` — מועתק ל־core.js). אחרי כל שינוי בקבצים: `node tools/coregen.js` ואז `node tools/swgen.js` — כותב ב־`sw.js` את `CACHE_NAME` ואת `HASHES` (SHA‑256, 32 תווי hex, לכל קובץ ב־`APP_SHELL`/`LIB_SHELL`/`STUDIO_SHELL`). **לא עורכים את הבלוק `<swgen>` ביד.**
2. **ההתקנה בטלפון מאמתת כל קובץ** (`fetchVerified`): ‎`?v=<טביעה>` (כתובת חדשה ל־CDN) + `cache:'reload'` + השוואת SHA‑256. המעטפת הכל־או־כלום — קובץ ישן/חסר = ההתקנה נכשלת, הגרסה הקודמת נשארת, ובדיקת העדכון הבאה (`reg.update` בפתיחה ובחזרה לאפליקציה) מנסה שוב. הספרייה/הסטודיו — קובץ שלא אומת לא נשמר. **לכן תוכן ו־`sw.js` באותו PR בטוחים**; עד v393 ההתקנה לקחה מה שהגיע (`addAll`) והמשיכה גם בכישלון — זו הייתה ה"הרעלה".
3. PR אחד ("1.3.0 (412): …" / "(412): …") → CI ירוק (כולל `deploy-guard` ו־`tests/swgen.test.js` — שכחת swgen = אדום) → המשתמש ממזג → **ה־workflow ‏`deploy`** (מ־v395; עד v394 — `release`): רץ רק אחרי שהבדיקות (`tests`) ירוקות על main → **סביבת הניסוי** (העלאה ישירה מ־Actions עם wrangler מקובע לפרויקט Cloudflare Pages ‏`thesnowball` — רק קבצי git של הקומיט שנבדק, ואז `swgen.js --live` על `STAGING_URL` או `thesnowball.pages.dev`; בלי הסוד `CLOUDFLARE_API_TOKEN` + המשתנה `CLOUDFLARE_ACCOUNT_ID` — מדלג. **לא החיבור ל־Git של Cloudflare**: הוא פורס כל דחיפה לפני הבדיקות, ובטלפון נתקע בלולאה בין Cloudflare ל־GitHub — 12/10/2026) → **אישור המשתמש** (סביבה `production`, "Review deployments" בטלפון; מיזוג חדש מבטל את ההמתנה הקודמת) → **GitHub Pages מאותו קומיט** (Pages → Source = GitHub Actions — הוגדר 12/10/2026) → אימות חי של כל קובץ ו**תגית git ‏`vX.Y.Z`** (גרסת המערכת; עד v394 התגית הייתה מספר הבנייה). **האישור מתבקש רק כש־`APP_RELEASE` עלה**; מיזוג בלי שחרור — הניסוי בלבד. ריצה אדומה = לבדוק; **אחרי מיזוג — לומר למשתמש לאשר את ה־deploy**.
4. חזרה לגרסה קודמת = התוכן של התגית הקודמת **כגרסה חדשה** (מספר גבוה יותר).
5. **הסשן לא דוחף ל־`main` בעצמו** — מנגנון הבטיחות בסשן ענן חוסם ("Production Deploy"); לא עוקפים ולא מנסים בכלי אחר. תמיד PR שהמשתמש ממזג מהטלפון.
6. שינוי במעטפות (`APP_SHELL`/`LIB_SHELL`/`STUDIO_SHELL`) — אחריו `node tools/swgen.js`; קובץ חדש שהאפליקציה טוענת בפתיחה — במעטפת.
7. **סביבות (שלב 2, v395)**: אותם קבצים בכל הסביבות; הסביבה לפי הכתובת ב־`firebase-config.js` (`window.SNB_ENV`: `prod` — github.io/thesnowball.app, `staging` — staging.thesnowball.app ו־`*.pages.dev`, `local` — localhost כמו prod). בניסוי: פרויקט Firebase נפרד (`STAGING_FIREBASE` = `snowball-staging-758f6`, מ־v396: Google בלבד, דומיינים מאושרים staging.thesnowball.app + thesnowball.pages.dev, אותם כללי Firestore — שינוי כללים = לפרסם בשני הפרויקטים), תווית "סביבת ניסוי" (`.env-strip`), אותו שרתון בינתיים (רק מידע ציבורי — ההתחברות של הניסוי לא מאומתת מול פרויקט הייצור). **כתובת/פרויקט חדשים לפי סביבה — רק שם**, לא קבוע ב־app.js; השרתון מקבל את כתובות הניסוי (`STAGING_ORIGIN_RE` ב־`lib/ibkr.js`, ועוד ב־`SNB_EXTRA_ORIGINS`). פרויקט Firebase לניסוי = גם ה־authDomain שלו ב־CSP. בדיקה: `tests/env-stage2.test.js`. **2ב (12/10/2026)**: השרתון והעובד של הניסוי — חדרים על שרת Hetzner משלו (`snb-stg-1`) מאחורי Cloudflare Tunnel, `https://api-staging.thesnowball.app`, Firebase ודלי R2 (`snb-staging`) של הניסוי; מושכים את `dev` בכל מיזוג, בלי אישור. ההקמה — workflow ‏`server` (infra/README.md, "שרת הניסוי").
8. **בדיקה חובה לפני שינוי ב־`sw.js`**: `tests/swgen.test.js` מריץ את ההתקנה ב־vm (קובץ ישן נדחה, 404 נדחה, הספרייה בשימוש). בדיקה בטלפון אחרי הפריסה הראשונה של כל שינוי בהתקנה.

**מגבלת פריסות של Vercel (לקח v213)**: בתוכנית החינמית יש מכסת פריסות יומית, וכל push (גם של sw.js/בדיקות) צרך פריסה → "Deployment rate limited — retry in 24 hours" והשרתון נשאר על הגרסה הקודמת בזמן שהאפליקציה כבר עודכנה. מאז: `ignoreCommand` ב־`ibkr-proxy/vercel.json` מדלג על commit שלא נוגע ב־`ibkr-proxy/`. לבדוק סטטוס פריסה: `api.github.com/repos/<repo>/commits/<sha>/statuses` (context Vercel). שינוי בשרתון — לאמת את התוצאה החיה (לא רק 200). **לקח v277**: `HEAD^` בדק רק את הקומיט האחרון בדחיפה — שני קומיטים בדחיפה אחת, והאחרון לא נוגע בשרתון → הפריסה בוטלה ושינויי השרתון לא עלו. מאז `ignoreCommand` משווה ל־`VERCEL_GIT_PREVIOUS_SHA` (הפריסה המוצלחת האחרונה; בלי — פורס). **לקח v285**: Vercel משכפל רק כמה קומיטים אחרונים — כשהפריסה המוצלחת האחרונה רחוקה, `git diff` נכשל ב־"bad object" (exit 128) ו־Vercel שולח "Production deployment failed" במייל בכל דחיפה (השרתון עצמו ממשיך לעבוד על הגרסה הקודמת). מאז `ignoreCommand` = `sh ignore-build.sh` (ב־`ibkr-proxy/`): מעמיק את ההיסטוריה, ואם עדיין חסר — רשימת הקבצים מ־GitHub compare; בכל ספק פורס, אף פעם לא קורס (רק exit 0/1). **15/10/2026 — רק main נפרס** (`git.deploymentEnabled` ב־vercel.json: `"**": false, "main": true`; גיבוי ב־ignore-build.sh לפי `VERCEL_GIT_COMMIT_REF`): תצוגות מקדימות של ענפים גמרו את מכסת 100 הפריסות ביום ("api-deployments-free-per-day"), והשרתון נשאר על גרסה ישנה. הודעת "Deployment failed" של Vercel על PR — לא אומרת שה־PR שבור. `tests/vercel-main.test.js`.
