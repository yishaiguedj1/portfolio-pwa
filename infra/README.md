# שרת התרגום — השרת כקוד

השרת שמריץ את סטודיו התרגום במצב "API של המערכת": Hetzner CX43 בגרמניה, Debian 13, ועליו קונטיינר אחד (העובד).
כל מה שעל השרת מוגדר בקבצים כאן. שרת שנמחק — מקימים מחדש בעשר דקות מאותם קבצים.

## איך זה עובד

- **השרת לא מקבל חיבורים.** אין לו אף פורט פתוח, גם לא SSH. הוא פונה החוצה בלבד:
  - שואל את השרתון (Vercel) כל 20 שניות אם יש עבודה (`translator/agent.py`).
  - מוריד את הסרטון מה־Drive שלך, מתמלל ומיישר בעצמו, ושולח ל־Claude רק את עבודת השפה (`job.py auto`).
  - מעלה את התוצרים ל־Drive ומדווח לשרתון. בסוף כל עבודה **כל הקבצים נמחקים מהשרת**.
- **עדכונים:** כל רבע שעה השרת בודק אם יש גרסה חדשה שאישרת (`snb-update`). הוא מתקין אותה רק אם החתימה שלה מוכיחה שנבנתה ב־GitHub מהענף הראשי, ורק כשאין עבודה באמצע.
- **עדכוני אבטחה של המערכת:** אוטומטיים כל יום. אתחול אחרי עדכון ליבה — בלילה, ורק כשאין עבודה (`snb-maint`).

## הדרך מקוד לשרת (פיתוח ← פרודקשן)

1. **פיתוח:** שינוי ב־`translator/` או ב־`infra/worker/` נכנס ל־`main`.
2. **בנייה:** `worker-image.yml` מריץ את הבדיקות. רק אם הן ירוקות הוא בונה את הקופסה פעם אחת, חותם עליה ומעלה ל־GHCR עם התג `dev`.
3. **אישור:** הקידום לפרודקשן (התג `prod`) מחכה לך. ב־GitHub בטלפון: Actions ← הריצה ← Review deployments ← Approve.
4. **פרודקשן:** השרת מושך את `prod` בתוך רבע שעה. **אותה תמונה בדיוק** שנבדקה — לא בונים מחדש.

**חזרה לגרסה קודמת:** ב־Actions פותחים ריצה ישנה של `worker-image` ומריצים שוב את `promote`. התג `prod` חוזר לתמונה הישנה, והשרת מתעדכן בתוך רבע שעה.

## אבטחה — מה מגן על מה

| הסיכון | ההגנה |
|---|---|
| חיבור לשרת מבחוץ | חומת אש בשרת (`host/nftables.conf`) + חומת האש של Hetzner: הכל חסום בכניסה. SSH כבוי. |
| קוד זדוני בגרסה | השרת מריץ רק תמונה חתומה מה־workflow בענף הראשי, ואחרי אישור שלך. |
| חבילה מזויפת | בסיס נעול ב־digest, ‏ffmpeg נבדק ב־sha256, כל ספריית Python נעולה בגרסה וב־hash. |
| תוכן לא מהימן בעבודה (תמליל, סרטון) | הקונטיינר: משתמש רגיל, בלי הרשאות (`cap_drop: ALL`), קבצי המערכת לקריאה בלבד, בלי גישה לשירות המטא־דאטה ולרשתות פנימיות. |
| פרצה בליבה של לינוקס מתוך העבודה | **gVisor** (`runsc`, ת2): ליבה מדומה סביב הקופסה — בשרת של 8GB ומעלה, אוטומטית (עד שלב 4.1 — 12GB) (`snb_runtime`). בדיקה עצמית לכל גרסה; נכשלה / שרת קטן / לא מותקן → `runc`, והסיבה מוצגת במסך השרת באפליקציה. כפייה: `echo runsc > /etc/snb/runtime` (או `runc`). נמדד 10/10/2026: תמלול +6%, יישור +26–39%, זיכרון בשיא +0.45GB; עם היישור ב־ONNX INT8 — שיא 4.2GB תחת gVisor. המאגר חתום במפתח שבריפו (`host/gvisor.key`). שרת שהוקם לפני כן — gVisor לא מותקן בו (קוד ההקמה רץ רק ביצירה): ליצור שרת חדש. |
| דליפת מפתחות | המפתחות רק ב־`/etc/snb/worker.env` (root, ‏600), לא בתמונה, לא בריפו ולא בהגדרה הראשונית. |
| חשבון Anthropic נפרץ / באג שמבזבז | תקרת הוצאה חודשית ב־Console של Anthropic + תקרה לכל עבודה בעובד (`budget_cap`). |
| נתוני משתמשים על השרת | נמחקים בסוף כל עבודה. נשארים רק מודלי התמלול (מטמון, בלי מידע אישי). |

## הקמה — פעם אחת

**א. חשבונות (בטלפון):**
1. **Hetzner:** הרשמה ל־Cloud, אימות דו־שלבי, ופרויקט ריק בשם `snowball`.
2. **Anthropic Console:** מפתח API בשם `snowball-server` ותקרת הוצאה חודשית (Limits). את המפתח שומרים לרגע ההדבקה בשרת.
3. **GitHub — אישור לפרודקשן:** Settings ← Environments ← New environment בשם `production` ← Required reviewers ← אתה. אחר כך Settings ← Secrets and variables ← Actions ← Variables ← New repository variable: `SNB_PROMOTE` = `on`. עד אז `prod` לא זז בכלל — מנעול נגד קידום בלי אישור.
4. **ניטור (רשות):** בדיקה חינמית ב־healthchecks.io עם תקופה של 10 דקות. מקבלים כתובת שמדביקים ב־`snb-setup`, ומייל כשהשרת מפסיק לפעום.

**ב. התמונה הראשונה:** אחרי המיזוג ל־`main` והאישור הראשון, ב־GitHub: הפרופיל ← Packages ← `snb-worker` ← Package settings ← Change visibility ← **Public**. אין בה סודות, והקוד ממילא ציבורי. כך השרת מוריד אותה בלי סיסמה.

**ג. יצירת השרת (Hetzner Cloud Console ← Add Server):**

| שדה | בחירה |
|---|---|
| Location | Nuremberg או Falkenstein (גרמניה) |
| Image | Debian 13 |
| Type | Cost-Optimized ← CX43 (Intel/AMD, 8 ליבות, 16GB). **כשאין CX במלאי:** Arm64 (Ampere) ← CAX21 (4 ליבות, 8GB — הכי זול) או CAX31 (8 ליבות, 16GB — מהיר פי ~2). התמונה בנויה לשתי הארכיטקטורות, והגבולות של הקונטיינר נקבעים לפי השרת (`snb_limits`). הגדלה בהמשך: Rescale ב־Hetzner, בלי התקנה מחדש |
| Networking | IPv4 + IPv6 (‏IPv4 נחוץ: GitHub עדיין בלי IPv6) |
| SSH keys | בלי |
| Firewalls | חדשה בשם `snb-closed`, **בלי אף כלל נכנס** |
| Backups / Volumes | בלי (אין על השרת מידע לשמור) |
| Cloud config | להדביק את **קוד ההקמה** מהאפליקציה (סעיף ד׳ למטה) |
| Name | `snb-worker-1` |

**ד. קוד ההקמה (לפני Create & Buy):** באפליקציה, בסטודיו: הגדרות ← השרת של המערכת ← השרת ← **הוספת שרת**. מדביקים בשדה את מפתח Anthropic ונוגעים ב־**העתקת קוד ההקמה**. האפליקציה מורידה את `infra/cloud-init.yaml` מהאתר ומכניסה בו את המפתח ואת טוקן השרת החדש (בטלפון בלבד; המפתח לא נשלח לשום מקום ולא נשמר). את הקוד מדביקים ב־Hetzner בשדה **Cloud config**. השרת עולה מוכן — מתקין, מאמת את החתימה ומתחיל לשאול את השרתון, **בלי קונסולה**. אחרי כמה דקות הוא מופיע במסך השרת כ"מחובר".

- **למה לא בקונסולה:** הקונסולה של Hetzner לא מעבירה הדבקה מהטלפון, ולא מציגה עברית.
- **מה זה אומר לאבטחה:** מה שב־Cloud config נשמר בשירות המטא־דאטה של Hetzner לכל חיי השרת. רק root בשרת מגיע אליו (הקונטיינר חסום בחומת האש), ומי שיש לו גישה לחשבון Hetzner ממילא שולט בשרת. לכן אין כאן חשיפה חדשה.
- **החלפת מפתח:** שרת חדש עם קוד הקמה חדש, ומחיקת הישן (עשר דקות). אפשר גם `snb-setup` בקונסולה (באנגלית), עם הטוקן שמוצג בחלק המקופל "הטוקן לבד".

## תפעול

- **מצב:** `snb-status` בקונסולה (גרסה, עבודה, דיסק, שורות אחרונות).
- **מחיקת השרת = החיוב נעצר.** כיבוי בלבד ממשיך לחייב. החיוב לפי שעה, עד תקרת המחיר החודשי.
- **גדילה:** עדיף שרת נוסף (אותה הגדרה, ‏`snb-worker-2`) על הגדלת השרת הקיים. הגדלה מעבירה אותו למחירון החדש.
- **שרת ניסויים:** לפני שינוי גדול אפשר להקים שרת לשעה מאותה הגדרה (עלות של סנטים) ולמחוק אותו.
- **החלפת מפתח Anthropic בשרת קיים (בלי שרת חדש):** בקונסולה של Hetzner (מהמחשב — שם ההדבקה עובדת) ‏`snb-setup`: מדביקים את המפתח החדש, ו־**Enter** בשאלות על הטוקן ועל הפעימה משאיר את מה שכבר בשרת. העובד עולה מחדש עם המפתח החדש; עבודה שרצה — המפתח מתחלף כשהיא מסתיימת. (שרת שהוקם לפני 10/10/2026 שואל גם על הטוקן — אז "הוספת שרת" באפליקציה נותנת טוקן חדש, ואחרי שהשרת מתחבר מסירים את הרשומה הישנה.)
- **גישת ניהול מהטלפון (רשות):** Tailscale. ‏`curl -fsSL https://tailscale.com/install.sh | sh && tailscale up --ssh` מהקונסולה. SSH פתוח רק ברשת הפרטית, כבר מותר בחומת האש.

## עדכון רכיבים

- **ספריות Python:** עורכים את `worker/requirements.in`, ואז (מהשורש):
  `uv pip compile --generate-hashes --python-version 3.12 --python-platform x86_64-manylinux_2_28 --index-strategy unsafe-best-match --no-emit-index-url --no-strip-extras -o infra/worker/requirements.lock infra/worker/requirements.in`
  ואז הקובץ של Arm, על **אותן גרסאות בדיוק** (מתוך `infra/worker`):
  `grep -E '^[a-z]' requirements.lock | sed 's/ \\$//; s/\[[^]]*\]//' > pins.txt && uv pip compile --generate-hashes --python-version 3.12 --python-platform aarch64-manylinux_2_28 --index-strategy unsafe-best-match --no-emit-index-url --no-strip-extras -c pins.txt -o requirements-arm64.lock requirements.in; rm pins.txt`
  (הבדיקות נכשלות אם הגרסאות בשני הקבצים שונות.)
- **תמונת הבסיס:** מחליפים את ה־digest ב־`worker/Dockerfile` (גרסת Python זהה).
- **הגדרת השרת (`host/`, `compose.yaml`):** אחרי כל שינוי: `python3 infra/build-cloud-init.py`. הבדיקות נכשלות אם שוכחים. הקבצים בקוד ההקמה דחוסים (gzip, ‏`encoding: gz+b64`) — עם חדרי הניסוי הם עברו את 32KB של Hetzner. המקור הקריא נשאר כאן. שרת קיים לא קורא את ההגדרה הראשונית שוב — שינוי כזה = שרת חדש מאותה הגדרה, ומחיקת הישן.
- **ffmpeg:** ה־workflow לוקח את ה־sha256 של הבנייה הנוכחית של ענף 8.1, לכל ארכיטקטורה, ורושם אותם בתוויות התמונה (`snb.ffmpeg.sha256.amd64`/`.arm64`). כל ארכיטקטורה נבנית על מכונה מהסוג שלה (`ubuntu-24.04-arm` — בלי אמולציה), וה־job ‏`merge` מאחד וחותם על ה־index.

## שרת הניסוי (שלב 2ב, 12/10/2026)

שרת שמריץ את סביבת הניסוי (`staging.thesnowball.app`) בשלושה חדרים נעולים, כל אחד ברשת משלו:
- **ה־Tunnel** (Cloudflare): החיבור היחיד מבחוץ, והוא **יוצא** מהשרת. גם כאן אין אף פורט פתוח.
- **השרתון של הניסוי**: אותו קוד כמו ב־Vercel (`ibkr-proxy/server.js`), עם Firebase, דלי R2 וסודות של הניסוי.
- **העובד של הניסוי**: אותה קופסה כמו בייצור, עם תקרות קטנות ומפתח Anthropic עם תקרה נמוכה.

**ניסוי = כל מיזוג.** השרת מושך את התג `dev` (גם של `snb-worker` וגם של `snb-app`) בלי אישור. הייצור ממשיך למשוך רק את `prod`.
**החדרים לפי קובצי הסודות** (`/etc/snb/*.env`): `worker.env` = עובד הייצור, `tunnel.env`, ‏`app-stg.env`, ‏`worker-stg.env` = הניסוי. שרת אחד יכול להריץ את כולם. אז עובד הניסוי מקבל 3GB וליבה וחצי, והשאר לייצור (`snb_limits`).
**ההקמה מ־GitHub ולא מהשרת:** Actions ← `server` ← Run workflow ← אישור. ה־workflow רושם טוקן שרת ב־Firestore של הניסוי, בונה את קוד ההקמה עם הסודות, יוצר את השרת ב־Hetzner ומחכה שהשרתון יענה ושהעובד יתחבר.

**פעם אחת — מה צריך (בטלפון):**
1. **Hetzner:** Security ← API tokens ← Generate (Read & Write) → הסוד `HCLOUD_TOKEN`.
2. **Cloudflare Tunnel:** Zero Trust ← Networks ← Tunnels ← Create ← Cloudflared, בשם `snb-stg`. מעתיקים את הטוקן (המחרוזת הארוכה אחרי `--token`) → הסוד `STG_TUNNEL_TOKEN`. ב־Public Hostname: ‏`api-staging` · ‏`thesnowball.app` · ‏HTTP · ‏`app-stg:3000`.
3. **R2:** דלי `snb-staging` ב־EU, עם CORS ל־`https://staging.thesnowball.app` ול־`https://thesnowball.pages.dev` (GET/PUT/HEAD, כותרות `*`, חשיפת `ETag`). מפתח Object Read & Write לדלי הזה בלבד → `STG_R2_ACCESS_KEY_ID`, ‏`STG_R2_SECRET_ACCESS_KEY`.
4. **Firebase (הניסוי):** Project settings ← Service accounts ← Generate new private key → כל תוכן הקובץ בסוד `STG_FIREBASE_SA`. הכלי מסרב לחשבון של פרויקט אחר.
5. **Anthropic:** מפתח נפרד עם תקרה נמוכה → `STG_ANTHROPIC_KEY`.
6. **המייל שלך** (מנהל בניסוי) → `STG_ADMIN_EMAIL`.
7. **GHCR:** אחרי הריצה הראשונה של `app-image` — Packages ← `snb-app` ← Change visibility ← Public (כמו `snb-worker`).

כל הסודות: Settings ← Secrets and variables ← Actions ← New repository secret. `CLOUDFLARE_ACCOUNT_ID` כבר קיים.
**בדיקה:** `https://api-staging.thesnowball.app/healthz` מחזיר `ok`, והשרת מופיע "מחובר" במסך השרת בסטודיו של הניסוי.

## החיבור לאפליקציה

- **טוקן השרת:** נוצר ב"הוספת שרת" (למנהל בלבד) ונכנס לקוד ההקמה. מוצג פעם אחת, ובשרתון נשמר רק ה־hash. "הסרה" באותו מסך — הטוקן מת מיד.
- **מסך השרת:** מחובר / מושהה / לא מחובר, גרסה, דיסק, זיכרון ומה הוא מתרגם עכשיו. מתעדכן מהדופק: כל 20 שניות כשהשרת פנוי, וכל 5 דקות באמצע עבודה.
- **תקציב:** לכל משתמש תקציב חודשי (`STUDIO_API_USER_MONTH_USD` ב־Vercel, ברירת מחדל 30$), ותקרה לכל עבודה (5/10/20/50$, לא יותר ממה שנשאר החודש). מעליהם — תקרת ההוצאה ב־Console של Anthropic.
- **עלות השרת עצמו** קבועה (€16.49 לחודש, כולל IPv4) ולא תלויה במספר העבודות, ולכן לא מחולקת לכל עבודה בכרטיס העלות.
